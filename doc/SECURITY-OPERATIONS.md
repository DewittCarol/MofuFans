# 上线与日常安全指南

[返回 README](../README.md) · [部署步骤](DEPLOYMENT.md) · [应用防护详情](SECURITY.md)

这份指南供站长和协助部署的 AI Agents 使用。可以把网址或文件交给你的 AI，要求它逐项检查并给出验收记录。没有服务器经验时，先在本机或仅自己可访问的环境试用；完成下面的上线检查后，再向粉丝开放。

本指南不是自动执行脚本。不同服务器、面板和代理的操作不同；不要把示例命令中的路径、域名或 IP 原样当成自己的配置。暂时查不到的项目应记录为“未验证”，不能当成已完成。

## 1. 哪些由项目提供，哪些需要另外配置

| 防护 | 项目内已提供 | 部署者还需要做什么 |
| --- | --- | --- |
| 网站登录与接口 | 身份与权限检查、默认限速、失败冷却、临时封禁 | 设置独立强密码；核对可信代理与真实来源IP；不要移除鉴权来解决访问问题 |
| 初始化 | 一次性安装码，无默认管理员 | 在自己控制的访问环境完成初始化，不公开安装码 |
| 会话 | 管理员会话服务端12小时到期；改密撤销旧会话；管理员账号管理和手动封禁需五分钟内密码确认 | 并非所有敏感操作都有二次确认；配置HTTPS并开启HTTPS Cookie，妥善保管密码和已登录设备 |
| 上传与连接 | 文件校验、大小／并发／读取进度限制，实时连接资源限制 | 预留磁盘、设上传用途和预算、监控空间；不代表已提供病毒扫描或总磁盘配额 |
| 安全记录 | 所有者后台“安全”页、有限事件与持久化封禁 | 保留状态目录，检查异常；按需要另设日志轮转和告警，页面不提供完整请求审计 |
| 服务器登录 | 不由网站管理 | SSH、系统账户、云账户、面板、Docker、数据库分别加固 |
| 网络与流量 | 应用和Nginx模板可减少业务处理消耗 | 防火墙、云安全组、CDN／流量防护及费用告警；应用无法阻止流量先到达服务器 |
| 数据与恢复 | 敏感字段加密；提供升级／恢复说明 | 数据、密钥、配置、附件一起备份，限制权限，并实际测试恢复 |

基础应用限速与封禁默认生效，不必先安装 Fail2ban。服务器仍可用 Fail2ban 保护SSH等入口；已有防护应保留。当前没有TOTP／Passkey或设备会话清单，不能用限速抵消密码泄露的风险。具体阈值、范围和恢复命令见[应用防护详情](SECURITY.md)。

当前只支持**单个Go API实例**。即使用MySQL和OSS，也不能直接扩成多个API副本：部分队列和限速在进程内，本地安全状态还有文件锁，不能把共享数据库等同于支持多实例。

## 2. 开放公网前必须完成

### 先掌握访问入口和恢复方式

- 确认服务器、域名、云账户及部署目录由自己控制；云平台、域名服务商、代码托管及面板支持双重验证时应开启。
- 保留可用的服务器控制台或其他恢复入口。修改SSH、防火墙或代理前，先保留一个可用会话，验证新入口后再关闭旧入口，避免把自己锁在外面。
- 原生部署使用仓库的专用服务用户和systemd模板；容器部署使用随附Compose。不要把Docker管理接口或Docker socket暴露给网站／公网，也不要直接把容器改成特权模式。

### 只开放需要的服务

- 公网通常只需要网站80／443，以及确实使用且来源受限的SSH／管理入口。SSH可使用其他端口，但换端口不能代替身份验证。
- Go API、MySQL、开发服务器和管理面板不要直接向所有来源开放。默认Compose站点端口为宿主机 `127.0.0.1:8088`，默认原生API为 `127.0.0.1:8080`；反向代理负责对外服务，不要只为方便把回环绑定改成所有地址。
- 核对云安全组、系统防火墙、IPv4与IPv6，以及Docker实际发布的端口。不要只看到面板或防火墙“已开启”就认为端口没有暴露；用自己控制的外部网络验证。
- SSH优先使用独立密钥和普通用户加sudo。确认密钥登录和恢复入口可用后，再按实际需要禁用密码登录、禁止root远程直登。不要盲目修改SSH配置，也不要把私钥放进网站目录、Git仓库或下载包。

### 使用HTTPS和正确的代理链

- 使用自己的域名和有效证书，浏览器不应出现证书警告；续期方式及到期检查要可用。经CDN访问时也要核对回源连接，不能只看浏览器地址栏的锁图标。
- 先完成域名、反向代理和证书，并通过HTTPS实际打开后台，再在“系统设置 → 部署与集成”开启“仅通过HTTPS传输登录Cookie”，通过HTTPS重新登录确认正常。不要在纯HTTP本机调试或HTTP的SSH转发访问中提前开启，否则Cookie不会经HTTP发送，可能无法继续登录。
- 同域部署时 `server.allowed_origins` 留空。确需跨域时只填写实际来源，不使用通配来源或为了消除报错放宽来源检查。
- 按[可信代理说明](SECURITY.md#管理员与会话)配置 `server.trusted_proxies`。它决定应用是否信任代理提供的访客IP；默认只信任回环地址，程序拒绝 `0.0.0.0/0`、`::/0` 等全地址配置。只填受控代理，Docker网桥、面板或CDN链路需要逐跳核对；各代理也应按其受控上游还原来源，不直接采信访客自行填写的IP头。
- 在后台“安全”核对当前识别的IP是否符合自己的出口和代理链。必要时从家庭宽带与手机流量等两个自己控制的网络比较；共享出口显示同一IP可能正常，但公网访客都变成回环／网桥IP会共用限额并可能一起被封，应先排查。不要靠伪造 `X-Forwarded-For` 验收真实IP，也不要为让限速恢复正常而简单放宽全部网段。
- 使用CDN且希望隐藏或限制源站时，另行核对源站可达范围、代理网段及证书续签方式；打开代理开关本身不会自动阻止绕过CDN直连。

### 保管账号、配置和数据

- 管理员使用密码管理器生成的独立随机密码，至少15字符，不与其他网站复用。新设密码会检查长度，旧账号不强制改密，升级站点需另行核对原有弱密码。多人维护各用独立账号，只给必要权限；不把所有协作者都设为站点所有者。
- 第一次认领应在仅自己可访问的通道完成，例如[部署说明中的SSH转发](DEPLOYMENT.md#docker-compose)，容器和原生部署均可按自己的端口使用。安装码只用于本次引导，不公开含安装码的日志或截图；认领完成后入口自动关闭，确认无法再次认领，再开放访问。
- 保留 `data/instance.json`、`data/settings.json`、部署配置、数据库、上传文件和 `data/security/`。这些内容只能由必要的服务账户和维护人员访问。OSS或MySQL模式也仍需持久化本地状态目录，并保持单API实例。`data/instance.json`含实例密钥，丢失或重新生成加密密钥后，已有地址等加密数据无法用新密钥恢复。
- Nginx静态根目录只指向构建出的前后台页面，不要指向项目根目录或把 `data/`、配置、备份、日志及整个上传目录直接公开。私密附件应继续走应用权限检查。
- OSS使用私有Bucket和仅能访问本站所需前缀的凭据；AI、云服务和数据库也使用本站独立凭据及最小权限，按需设置额度／费用告警。不要把生产秘密交给不受信任的AI、插件或公共问题帖。
- 提交前检查配置、环境文件、数据库、私钥、访问令牌、地址和私信是否进入Git；运行 `python3 scripts/check-release.py` 后仍需人工核对。`.gitignore` 不会移除已经提交的秘密，删除文件或重写历史也不能替代撤销泄露凭据。

### 备份并试一次恢复

按[备份说明](DEPLOYMENT.md#备份)保存数据、配置与原密钥。运行中SQLite使用backup API／`.backup`，不能只拷仍有WAL的主库；不熟悉时先停服再备份整个私有数据和配置目录。MySQL和OSS需各自备份，不能只打包网站代码。

至少保留一份在服务器之外且受限访问的副本；根据可接受的数据损失安排备份频率。放在同一块磁盘上不能应对整机／磁盘丢失。备份含秘密和个人信息，也需要访问控制及适当加密。

首次上线和重要升级前，在隔离副本恢复一次：确认旧密钥可解密数据、附件可读、管理员可登录。恢复测试须关闭真实私信队列和其他对外任务，使用自己的合成数据或受限副本；不要让恢复副本再次群发。记录最近一次成功恢复时间。

副本隔离应在启动前完成，必要时限制测试环境出站网络，防止从恢复的生产凭据继续调用外部服务；不要只依赖操作人员记得不点击发送。相关设置只用于测试副本，不擅自改变正式站任务状态。

## 3. 给协助部署的AI Agents

开始部署、修改代理／权限、升级、恢复或处理安全事件前，阅读本文件、[AGENTS.md](../AGENTS.md)、[部署](DEPLOYMENT.md)、[应用防护](SECURITY.md)和[升级说明](UPGRADING.md)。遵循站点所有者的授权范围，咨询和检查不自动等于允许停服、改密、发私信或删除数据。

1. **先盘点再改。** 只读取任务需要的信息：OS／架构、部署方式、服务用户、监听与发布端口、代理链、配置优先级、持久目录、运行版本、备份与恢复入口。未知项列出，不猜环境。命令里的实际路径、服务名、端口必须来自该实例，不直接套用示例。
2. **将实例资料放私有位置。** 不把生产密钥、用户地址、Cookie或连接资料写回本仓库、公共Issue、CI附件或聊天报告。日志脱敏，必要证据限制访问；不要上传完整服务器配置来寻求普通排错帮助。
3. **变更可恢复。** 先备份并记录版本、配置及回退方式，再做范围明确的增量改动。保持单API实例，不因使用OSS／MySQL就扩副本。不要因应用已有封禁就关闭防火墙／Fail2ban，不用 `chmod 777`、关闭TLS验证或绕过鉴权解决报错，不为重启重新生成实例密钥。改SSH／防火墙保留恢复入口，先校验配置再重载。
4. **离线检查和真实验收分开。** 构建／单元测试／模拟上游通过不能写成真实B站、AI、MySQL或OSS均可用。只使用自己控制的测试账户，不对真实名单群发，不在生产执行压测、爆破或批量错误登录。防护阈值测试放隔离环境，避免触发正常站点封禁或上游风控。
5. **核对实际效果。** 检查实际端口暴露、HTTPS／Cookie、匿名拒绝和跨账号隔离、真实IP、状态持久化、附件保护、备份及日志轮转。HTTP状态与JSON业务码都要看；公开的主题等接口返回200是正常的，私密数据接口不能匿名读取。
6. **逐项交付。** 将每项标为“已验证／未验证／不适用”，附非敏感证据和未完成原因。未完成的必要上线项要告诉站长，不用“测试全绿”代替公网部署验收。证据和实际实例路径放私有运维记录，公开文档只留通用说明。

可直接交给AI的任务：

> 请按本仓库 AGENTS.md 和 doc/SECURITY-OPERATIONS.md 检查我的部署。先确认实例、代理、数据目录、备份及可恢复的管理入口，再在授权内配置安全措施。不要泄露凭据、对真实粉丝发测试消息、重置实例密钥或用旧库覆盖新数据。完成后逐项给出已验证／未验证／不适用和脱敏证据；需要停服、改密、删除或扩大权限时说明实际影响，并遵循我给出的授权。

## 5. 上线后如何维护

- 经常检查“安全”页的持续失败、频繁封禁、持久化异常及当前IP；事件短时合并、最多1000组且最长七天，容量用满可能更早移出旧记录，不是全量日志，不能据“没有记录”断定从未被攻击。该页也不负责自动通知你，服务器监控与告警需另设。
- 为系统和代理日志、Docker日志配置大小／保留期，监控磁盘、CPU／内存、流量与外部服务额度；备份容量也要计入。持续异常先看原因，不靠不断重启或清空封禁应付。
- 按使用频率检查备份与告警，定期更新OS、Docker、代理和项目；每次升级保留原密钥、同批更新API及前后台，先备份并演练。依赖扫描只反映已知漏洞，不能保证没有逻辑问题。
- 撤销离任协作者权限，检查不再需要的SSH密钥、云令牌和外部服务凭据。不要把备份、旧构建和未受保护的预览站留在公开目录。

## 6. 被封禁、出现异常或疑似入侵时

**误封或登录失败：** 先看 `Retry-After` 和“安全”页的范围，核对密码、时间、来源IP和代理；不要连续重试。后台不可用时，先停止API，再按[停服恢复命令](SECURITY.md#安全记录误封与本地恢复)解除指定封禁，完成后启动API。它不解除服务器／CDN封禁，也不修复损坏状态文件；不要删除整个状态目录或业务库来“重置”。

**疑似被入侵：**

1. 记录发现时间、受影响入口和脱敏证据，保留日志与当前配置／数据副本。必要时限制受影响入口或暂时停止公开服务，避免继续泄露和写入；不要先清日志、重装系统或覆盖数据库。
2. 从可信设备核对云／SSH登录、应用管理员操作、权限与凭据变动、文件／服务／定时任务及异常流量。网站攻击请求、成功越权、主机登录是不同证据，不能只凭一个IP或一次200响应下结论。
3. 对确认或可能泄露的密码、云令牌、SSH密钥、B站Cookie、AI／OSS凭据逐项撤销或轮换并验证旧凭据失效。**地址等数据加密密钥不能直接换掉**；先保存旧密钥和一致备份，评估受影响数据并制定迁移／重新加密方案。
4. 修复入口后在隔离环境验证。涉及主机失陷时，应评估用可信系统重建，而非只改网站密码；恢复只导入已核对的数据和配置，不把可疑脚本或旧漏洞一并恢复。涉及用户个人信息时，按实际影响履行适用的通知与处理义务。
5. 恢复前完成上线清单，并补记事件范围、已确认与未确认结论、修复、凭据处理、恢复及观察结果。不把旧整库覆盖到已有新地址／领取／发送结果的库上。

不确定如何处理时，将本节交给可信维护人员或AI协助取证；分享最少必要的脱敏材料，不公开完整日志、用户信息或密钥。
